# Итерация 2: терминальный консультант

Источник обновления: новая копия Roberta, предоставленная 16 октября 2026 года. Из неё использованы схема каталога и идея структурированного состояния обращения в SQLite. Исходная папка не изменяется.

## Перенесено и адаптировано

- `knowledge_base.json`: 51 карточка в структуре новой версии; цены, описания и периоды сверены с ранее собранным каталогом. Непрочитанная цена остаётся `null`.
- `persona.example.json`: публичные правила продаж вместо персонажа для личной переписки. Старый приватный `persona.json` не используется.
- Модель возвращает `messages` и `crm_state`. Схема проверяется до сохранения; некорректный ответ заменяется безопасной репликой.
- Состояние предыдущего хода передаётся обратно в модель. Это предложение модели, которое может содержать ошибки, а не проверенные CRM-факты.
- Полная локальная история сохраняется при сжатии; сводка и её checkpoint хранятся отдельно. Команда `/forget` очищает историю, сводку и карточку текущей сессии.
- Ядро диалога отделено от Telegram. Основной сценарий: интерактивный терминал через Polza.ai, с общим журналом запросов и лимитами.

## Что не перенесено

- Автоматическая отправка после 15 минут молчания: согласие на повторный контакт в новой версии не проверяется.
- Прямые уведомления администратору и JSONL-выгрузка в Bitrix24: пользователь пока согласовал терминал. Локальная запись не равна успешной доставке.
- Необоснованные обещания аттестата, зачисления немедленно, сроков ответа, месячных платежей и специального московского тарифа.
- Правило выбирать более дешёвую из конфликтующих ГИА-карточек: различия не установлены.
- Обязательный сбор телефона, email и регистрации в Москве для любого обращения.
- `.env`, Telegram-сессии, SQLite, переписки, логи, окружение, исполняемые файлы и старые инструкции запуска Roberta.

## Ошибки новой версии, учтённые при переносе

В исходном `upsert_lead` флаг запроса передачи сразу устанавливал `handoff_triggered`. Следующая проверка видела передачу как выполненную и могла вообще не отправить карточку. Сравнение контактов также происходило уже после перезаписи состояния. Кроме того, финальный флаг отправки выставлялся независимо от успеха внешних действий. В текущей итерации внешних действий нет; `handoff_requested` обозначает лишь намерение, а поле фактической доставки не заполняется моделью.

В исходной версии сжатие удаляло исходные сообщения, а парсер мог отправлять пользователю сырой JSON с CRM-полями при неправильной форме ответа. История теперь сохраняется, парсер отклоняет неправильный конверт целиком.

## Проверка и ограничения

Выполнена только статическая проверка: синтаксис Python через AST, JSON, полнота каталога, сопоставление цен и URL с предыдущим снимком, состав файлов и проверка паттернов секретов, `git diff --check`. Приложение, тесты, API и интеграции не запускались по указанию пользователя.

Добавлены офлайн-тесты ошибок JSON, типов полей, сохранения истории, очистки карточки, отсутствия фиктивной доставки, каталожных конфликтов, изоляции диалогов, общего бюджета и HTTP-контракта Polza. Их результаты пока неизвестны.

Проверка схемы не доказывает фактическую корректность естественного текста модели. Правила цен и рекомендаций пока задаются промптом; отдельный программный контроль фактов и полноценная проверка согласий ещё нужны перед клиентским пилотом. `requires_review` является предупреждением для модели, а не готовой системой разрешения заказа. Инструментов оформления здесь вообще нет.

Каждый запуск терминала создаёт отдельную локальную сессию; автоматического восстановления старых сессий нет. Общий лимит вызовов сохраняется между запусками. Сводка также расходует вызовы модели. Локальные базы не шифруются приложением; использовать вымышленные данные до согласования правил хранения. Автоматической очистки по сроку нет.

## Локальная настройка для следующего этапа

Требуется Python 3.10+. Команды ниже приведены как инструкция и в этой итерации не выполнялись:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
# Заполнить POLZA_API_KEY и точный POLZA_MODEL локально, без отправки ключа в чат.
.venv/bin/python -m evrika --chat
```

Не перезаписывайте существующий `.env` командой копирования. Без аргументов команда показывает справку; Telegram не запускается. `--preview` выводит публичный промпт без сети. `--chat` делает реальные платные API-запросы после ввода сообщения. Автоматический выбор модели и повтор запроса после ошибки отключены.

Команды диалога: `/state` показывает локальную карточку, `/usage` счётчики, `/stop` останавливает обработку, `/start` возобновляет, `/forget` очищает только текущую сессию, `/exit` завершает программу. `/state` является отладочным интерфейсом, не клиентской функцией.

Для будущей проверки: `.venv/bin/python -m unittest discover -s tests -v`. Эти тесты используют подменённый провайдер и не требуют реальных ключей.

HTTP-контракт проверен по [документации Polza](https://polza.ai/providers/openai): `POST https://polza.ai/api/v1/chat/completions`, Bearer-ключ, идентификатор модели из кабинета. Доступность выбранной модели, качество ответов, фактические расходы и соответствие JSON-формату предстоит проверить реальными диалогами.

Следующий этап: ручная проверка сценариев из `sales_scripts.txt`, уточнение спорных условий с заказчиком, затем отдельное подключение Telegram Bot API и CRM с подтверждаемыми статусами действий.
